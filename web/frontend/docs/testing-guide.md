# 프론트 개발/테스트 가이드

> `feature/ui` 브랜치를 pull 받은 팀원이 "이걸 어떻게 켜서 뭘 눌러보면 되는지" 알 수 있게 정리한 문서.
> 백엔드 API가 아직 없는 상태라, 모든 데이터는 **MSW(Mock Service Worker)** 가 브라우저에서 실제 fetch를 가로채서 응답합니다. 새로고침하면 데이터가 초기화되는 인메모리 mock입니다.

## 1. 실행 방법

```bash
cd web/frontend
npm install
npm run dev
```

브라우저에서 `http://localhost:5173` 접속.

```bash
npm run build   # 타입체크 + 프로덕션 빌드
npm run lint    # oxlint
```

## 3. Mock API 동작 원리

- `src/mocks/handlers/`에 화면(도메인)별로 핸들러 파일을 나눠 추가합니다. 실제 API 스펙(구글시트 `api 설계서` 탭 / `notion/api-contract.md`)의 endpoint·요청/응답 형식을 그대로 따릅니다.
- 개발 모드(`npm run dev`)에서만 자동으로 켜집니다 (`src/main.tsx`의 `enableMocking()`). 프로덕션 빌드에는 포함되지 않습니다.
- 콘솔에 `[MSW] Mocking enabled`가 뜨고, 이후 API 요청마다 `[MSW] ... (200 OK)` 형태의 로그 그룹이 남습니다 — **API 요청/응답을 확인할 때 브라우저 개발자도구 콘솔을 펼쳐보는 게 제일 빠릅니다.**
- 이메일 인증코드, 비밀번호 재설정 인증코드처럼 "실제로는 이메일로 오는" 값은 전부 **브라우저 콘솔에 `[mock] ... 인증코드: 123456` 형태로 출력**됩니다. 실제 이메일이 발송되지 않으니 콘솔에서 코드를 복사해서 입력하세요.
- 공연 목록의 카테고리 필터는 **API 파라미터가 아니라 프론트에서 클라이언트 사이드로 필터링**합니다. 구글시트 `api 설계서`의 PERF-001 스펙에 쿼리 파라미터가 없어서(`요청 파라미터: -`), 실제 백엔드가 카테고리 필터를 지원하게 되면 그때 서버 사이드 필터링으로 옮기면 됩니다. mock 공연 데이터는 `src/mocks/data/performances.ts`에 있습니다.

## 4. 화면별 테스트 시나리오

### 로그인 (`/login`)
1. `test@example.com` / `passwd123` 입력 후 로그인
2. 헤더 우측이 로그인/회원가입 버튼 → 아바타 메뉴로 바뀌는지 확인
3. 잘못된 비밀번호 입력 시 "이메일 또는 비밀번호가 올바르지 않습니다" 에러가 뜨는지 확인

### 회원가입 (`/signup`)
1. 새 이메일 입력 → "인증번호 발송" 클릭
2. 브라우저 콘솔에서 `[mock] {이메일} 인증코드: 123456` 확인 후 그 값을 인증번호 칸에 입력
3. 닉네임(2~20자) / 비밀번호(8자 이상, 영문+숫자 포함) / 비밀번호 확인 입력 후 제출
4. `/login`으로 이동하는지, 방금 만든 계정으로 로그인이 되는지 확인 (탭을 새로고침하지 않은 상태에서)

### 비밀번호 재설정 (`/password/reset`)
1. `test@example.com` 입력 → "인증번호 발송"
2. 콘솔에서 재설정 인증코드 확인 후 입력
3. 새 비밀번호 입력 후 제출 → `/login`으로 이동
4. 바뀐 비밀번호로 로그인되는지 확인 (테스트 후 다시 `passwd123`으로 되돌리려면 같은 과정을 반복하거나 새로고침으로 mock DB를 초기화)

### 공연 목록 (`/`)
1. 카드가 6개 보이는지 (mock 데이터, `src/mocks/data/performances.ts`)
2. 카테고리 칩(콘서트/뮤지컬/연극/전시) 클릭 시 클라이언트에서 필터링되는지
3. 헤더 검색창에 "재즈" 입력 후 Enter → 검색 결과만 보이는지, URL에 `?keyword=` 붙는지

### 공연 상세 (`/performances/:id`)
1. 공유하기 클릭 → 다이얼로그에 링크 표시 + 클립보드 복사
2. 비로그인 상태에서 하트(관심 공연) 클릭 → 로그인 유도 모달 → "로그인하러 가기" → 로그인 후 **원래 보던 상세 페이지로 자동 복귀**하는지 (Phase 1의 리다이렉트 기능)
3. 로그인 상태에서 하트 클릭 → 채워진 하트로 바뀌는지 (다시 누르면 해제)
4. "예매하기" 클릭 → 로그인 상태면 바로 회차 선택으로, 비로그인이면 로그인 모달

### 회차 선택 (`/performances/:id/schedules`)
1. 날짜별로 그룹핑되어 보이는지, 요일이 한국어(토/일)로 표시되는지
2. 잔여 좌석 0인 등급만 있는 회차는 "매진"으로 비활성화되는지 (뮤지컬 별의 시간 8/23 19:30 회차)
3. "선택" 클릭 시 `/schedules/:scheduleId/seats`로 이동하는지 (Phase 3에서 실제 화면 구현 예정)

### 대기열 → 좌석 선택 → Hold → 무통장입금 예매 (Phase 3)
1. 로그인 상태에서 공연 상세 → "예매하기" → 회차 "선택" 클릭
2. **대기열 화면이 뜨고 약 7초 후 자동으로 좌석 선택 화면으로 넘어가는지** (데모용으로 항상 짧게 대기하도록 만들어둠 — 아래 "설계 결정" 참고)
3. 좌석 배치도에서 범례 4가지(예매가능/선택중/선점중/판매완료) 색이 실제로 다르게 보이는지
4. 좌석 2~3개 선택 → 하단 바에 칩과 합계금액이 뜨는지 → 5석째 선택 시도하면 "최대 4석" 스낵바가 뜨는지
5. "선점하기" → 하단 바가 "선점 완료 · 남은시간 mm:ss" + "선택 취소"/"예매하기" 버튼으로 바뀌는지, 좌석 배치도에서 선택한 좌석이 검정(선택중)으로 유지되는지
6. "선택 취소" → 다시 좌석 선택 모드로 돌아가고, 방금 선점했던 좌석이 다시 "예매 가능"(흰색)으로 보이는지
7. 다시 좌석 선점 → "예매하기" → 무통장입금 폼에서도 같은 남은시간 카운트다운이 이어서 보이는지 → 입금자명 입력 후 제출
8. 예매 확인 페이지에서 예매번호/좌석/입금 은행·계좌·예금주·입금기한이 보이는지
9. (선택) Hold 만료: `src/mocks/data/store.ts`의 `HOLD_TTL_MS`를 잠깐 짧게(예: 15000) 바꿔서 재현 가능 — 실제 5분을 그대로 기다리긴 힘드니 로컬에서만 임시로 줄여서 확인하고 원래 값으로 되돌려둘 것

### Phase 3 설계 결정 (스펙에 없어서 프론트에서 임의로 정한 것들)

| 항목 | 결정 | 이유 |
|---|---|---|
| 대기열 대기시간 | 진입 시 항상 약 7초(`QUEUE_WAIT_MS`) 대기 후 READY | 실제로는 트래픽에 따라 가변이지만, 데모/테스트마다 대기열 화면을 매번 보여주면서도 너무 오래 기다리지 않도록 고정값으로 시뮬레이션 |
| entryTicket 캐시 | 스케줄별로 세션스토리지에 9분간 캐시 | 같은 세션에서 새로고침/재방문할 때마다 대기열을 다시 타지 않도록 |
| 좌석 최대 선택 수 | 4석 | 스펙에 명시 없음 — 일반적인 티켓팅 관례로 프론트에서 추가한 제약 |
| 좌석 상태 시드 | seatId가 7의 배수면 SOLD, 11의 배수면 HELD, 나머지는 AVAILABLE | 데모에서 3가지 상태를 항상 골고루 볼 수 있게 고정 시드 사용 |
| Hold TTL | 5분 (스펙 하한값 그대로) | RESV-003 비고의 "5~10분" 중 짧은 쪽 |
| **회차 → 공연/공연장 역참조** | **API 스펙에 없음.** 좌석 선택 화면은 회차 선택 화면에서 넘겨준 `performanceId`/`venueId`(location.state, 세션스토리지 캐시)에 의존. 이 state 없이 좌석 선택 URL에 직접 접근하면 "다시 선택해주세요" 안내만 뜸 | 백엔드에 이 조회 API가 생기면 그때 직접 URL 접근도 지원하도록 개선 가능 — **백엔드 팀에 공유 필요한 스펙 갭** |

### 발견 후 수정한 버그
Hold 남은시간이 로컬 타이머로는 0초가 됐는데, 서버가 실제로 좌석을 해제하기 전에 화면을 선택 모드로 돌려서 방금 만료된 좌석이 잠깐 "선점중(회색)"으로 보이는 레이스 컨디션이 있었음. 로컬 타이머가 0이 되면 서버에 즉시 재확인을 강제로 요청하고, **서버가 만료를 확인해준 뒤에만** 화면을 되돌리도록 수정함 (`useHoldCountdown.ts`).

### Front/Server 버전 · 서버 정보 (제출 필수조건)
아무 화면이나 들어가서 **맨 아래 푸터**를 보면 `Front v0.1.0 · Server v1.0.0-mock (api-a · ap-northeast-2a)` 형태로 보입니다. Server 쪽 값은 백엔드가 실제로 `/api/v1/version` 응답에 서버 식별 필드를 추가해주면 그 값으로 바뀝니다 (`docs/backend-decisions-needed.md` 4번 참고).

## 5. 트러블슈팅

**"요청에 실패했습니다" 같은 뭉뚱그려진 에러가 뜬다면:**
1. **새 Phase를 pull 받은 직후라면 `npm install`부터 다시 하고, `npm run dev`를 껐다가 다시 켜세요.** 새 npm 패키지가 추가된 상태에서 기존에 켜져 있던 dev 서버를 그대로 쓰면, Vite의 의존성 사전 번들링이 꼬여서 새로 추가된 화면의 API 요청이 실패하는 경우가 있습니다. (실제로 이 문제로 로그인이 막힌 사례가 있었습니다 — 원인은 코드 버그가 아니라 dev 서버를 재시작하지 않아서였습니다.)
2. 브라우저 개발자도구 콘솔을 열고 `[MSW] Mocking enabled`가 찍혀 있는지 확인합니다. 안 보인다면 **강력 새로고침(Ctrl+Shift+R / Cmd+Shift+R)** 후 다시 시도하세요.
3. 그래도 안 되면 개발자도구 Network 탭에서 실패한 `/api/v1/...` 요청의 응답이 JSON인지 HTML(404 페이지)인지 확인해주세요. HTML이 온다면 MSW가 그 요청을 가로채지 못했다는 뜻입니다 — 1번 방법으로 해결됩니다.

**콘솔에 뜨는 인증코드를 못 찾겠다면:** 문자열 `[mock]`으로 검색(콘솔 필터)하면 바로 찾을 수 있습니다.

# 백엔드와 맞춰야 할 것들

> 프론트(`feature/ui`)에서 화면을 mock API로 먼저 구현하면서 발견한, **백엔드 팀(다란/주연)과 같이 결정하거나 확인받아야 하는 부분**만 정리한 문서.
> 프론트 내부 개발 방식/테스트 방법은 [`web/frontend/docs/testing-guide.md`](../web/frontend/docs/testing-guide.md)에 있음. 여긴 "우리끼리 대화가 필요한 것"만.

## 어떻게 읽으면 되나요

각 항목은 **[현재 프론트 mock이 가정하고 있는 내용]** + **[왜 확인이 필요한지]** 순서로 적었습니다. 우선순위 순으로 정렬했고, 🔴는 실제 연동 전에 반드시 맞춰야 하는 것, 🟡는 알고만 있으면 되거나 여유 있을 때 맞추면 되는 것입니다.

---

## 🔴 1. 회차 → 공연/공연장 역참조 API가 없음

**현재 API 설계서(구글시트) 어디에도 "이 scheduleId가 몇 번 공연/공연장 소속인지" 조회하는 엔드포인트가 없습니다.**

- 좌석 배치도(`GET /venues/{venueId}/seat-map`)는 `venueId`가 있어야 호출 가능
- 좌석 상태(`GET /schedules/{scheduleId}/seats`)는 `scheduleId`만 있으면 되지만, 좌표(x/y)가 없어서 위 API와 조합해야 함(API-PERF-005 비고에 명시된 방식)
- 즉 **좌석 선택 화면에 `venueId`를 어디선가는 구해서 넘겨줘야 하는데, scheduleId 하나로 되짚어 갈 방법이 스펙에 없음**

**지금 프론트가 하고 있는 임시방편**: 회차 선택 화면(공연 상세를 이미 조회한 상태)에서 `venueId`/`performanceId`를 라우터 state로 들고 다니다가 좌석 선택 화면에 넘겨줌. 그래서 **좌석 선택 페이지 URL로 바로 들어오면(새로고침, 링크 공유 등) 정보가 없어서 "다시 선택해주세요" 화면만 뜸.**

**결정할 것**: 아래 둘 중 하나를 골라주세요.
- (a) `GET /schedules/{scheduleId}` 같은 조회 API를 하나 추가해서 `performanceId`/`venueId`를 바로 알 수 있게 하기 (추천 — 나중에 좌석 선택 URL을 카카오톡 공유 등으로 직접 열어도 정상 동작함)
- (b) 지금처럼 "공연 상세 → 회차 선택 → 좌석 선택" 순서로만 진입 가능하다고 못박기 (추가 API 없이 갈 수 있지만, 새로고침하면 처음부터 다시 눌러야 함)

## 🔴 2. 대기열 진입 조건과 방출 로직

**현재 프론트 mock은 "회차 선택에서 좌석 선택으로 넘어갈 때마다 무조건 대기열을 한 번 거치고, 약 7초 후 자동으로 통과"하도록 만들어뒀습니다.** 실제로는 트래픽이 몰릴 때만 대기열이 필요한 걸로 알고 있는데:

- 대기열을 항상 타야 하나요, 아니면 `QUEUE_ENABLED` 같은 플래그나 트래픽 임계치로 평소엔 건너뛰나요? (skeleton 지침 문서에 `QUEUE_ENABLED` 우회 플래그 얘기가 있던데, 이게 최종 방향인지 확인 필요)
- 방출 속도(몇 명씩/몇 초마다 READY로 전환하는지)에 따라 프론트의 "예상 대기시간" 문구 계산 방식이 달라짐
- `entryTicket`의 정확한 유효시간 — 프론트는 세션스토리지에 9분간 캐시해두고 재사용 중인데, 실제 TTL과 다르면 좌석 선점 시점에 403이 날 수 있음

## 🔴 3. Hold(좌석 선점) 이후 좌석 상태값

무통장입금 예매가 생성되면(`POST /reservations/bank-transfer`), 그 좌석은 어떤 상태가 되나요?

- 지금 프론트 mock: Hold → 예매 생성 즉시 `SOLD`(판매완료)로 바꿔버림
- 그런데 실제로는 "입금 대기중(PENDING_PAYMENT)"인 좌석과 "관리자가 입금 확인해서 확정(CONFIRMED)"된 좌석을 화면에서 다르게 보여줘야 할 수도 있음 (예: 입금기한 지나면 다시 `AVAILABLE`로 풀려야 함)
- `docs/seat-state-machine.md`(예정) 나오면 그 기준으로 프론트 색상/상태를 다시 맞출 예정 — **이 문서가 언제 나오는지, 상태값 이름을 뭘로 정할지 미리 맞추면 좋겠음**

## 🔴 4. Front/Server 버전 · 서버 IP·서버명 화면 노출 (제출 필수조건)

노션 프로젝트 문서의 "화면에 보여야 할 것" 항목에 `Front version, Server version`과 `서버 IP, 서버명`을 화면에 노출해야 한다고 되어 있습니다.

- `/health/live`, `/health/ready`는 k8s liveness/readiness probe 용도라 버전·서버 식별 정보가 없음 (`status`, `checks`만 반환) — 이 요구사항엔 안 맞음
- API 설계서의 **`GET /api/v1/version`(API-SYS-003)** 이 가장 가까운 후보. 원래 "모바일 앱 강제 업데이트 판단"용으로 설계됐지만, 이번 프로젝트엔 모바일 앱이 없으니 이 응답에 **서버 식별 필드를 추가로 얹어서 재사용**하는 걸 제안합니다.

**제안하는 응답 형태**:
```
GET /api/v1/version
{
  "apiVersion": "1.0.0",
  "server": { "instanceId": "api-a", "az": "ap-northeast-2a" }
}
```
`instanceId`는 `core/logging.py`에 이미 계획된 필드(api-a/api-c 구분용)와 값을 그대로 맞추면 새로 만들 것 없이 재사용 가능합니다.

**Front version은 백엔드 API가 필요 없습니다** — 프론트가 빌드 시점에 `package.json` 버전을 화면에 그대로 표시하면 됩니다.

프론트는 일단 이 응답 형태를 가정하고 mock으로 먼저 화면(footer)에 붙여뒀습니다. 실제 필드명/값이 다르게 정해지면 `src/pages/system/systemApi.ts` 하나만 고치면 됩니다.

## 🟡 5. 좌석 좌표(x, y)의 실제 의미

`venue_seat`의 x/y가 정확히 뭘 뜻하는지(픽셀 좌표? 그냥 열/행 순번? 곡선 좌석 배치 지원?) 스펙에 구체적인 정의가 없어서, 프론트는 **그냥 열 번호를 x, 행 번호를 y로 써서 CSS 그리드로 렌더링**하고 있습니다. 실제 공연장이 직사각형 그리드가 아니라 곡선/블록 형태라면 렌더링 방식을 바꿔야 하니, 실제 데이터 형식이 정해지면 알려주세요.

## 🟡 6. 좌석 선택 최대 개수 제한

스펙에 없는 내용인데, 프론트에서 "1인당 최대 4석"으로 임의로 제한해뒀습니다. 백엔드 `POST /seats/hold`도 같은 제한을 걸 건지 (안 걸면 프론트 우회해서 무제한으로 선점 가능) 확인 필요.

## 🟡 7. 입금 기한(`paymentDueAt`)

스펙에 구체적인 시간이 안 나와 있어서 프론트 mock은 예매 생성 시점 + 24시간으로 임의로 잡아뒀습니다. 실제 정책값이 있으면 알려주세요.

## 🟡 8. 무통장입금 계좌 정보

지금은 은행명/계좌번호/예금주를 고정값 하나로 mock 처리했습니다. 실제로도 고정 계좌 하나만 쓰는 게 맞는지, 아니면 공연/관리자별로 다른 계좌를 쓸 수 있어야 하는지 확인 필요.

## 🟡 9. Refresh Token 처리

API 설계서엔 Refresh Token을 HttpOnly + Secure + SameSite 쿠키로 관리한다고 되어 있는데, 프론트는 아직 accessToken만 메모리에 들고 있고 refresh 흐름은 구현 안 했습니다 (새로고침하면 로그아웃됨 — 지금은 mock 개발 단계라 의도적으로 단순화). 실제 연동 시점에 쿠키 도메인/SameSite 정책(프론트·백엔드가 같은 도메인 아래 있는지 등)을 같이 맞춰야 합니다.

## 🟡 10. 관리자 로그인 화면 위치

API 설계서 비고엔 "별도 도메인(admin.example.com)에서 로그인"이라고 되어 있는데, 지금 프론트는 일단 같은 앱 안에 `/admin/login` 라우트로 만들어뒀습니다. 실제 배포 때 서브도메인을 분리할 계획이면 그때 라우팅 구조를 바꿀 예정입니다 — 지금 단계에서는 몰라도 됨, 배포 전에만 확인.

## 🟡 11. 관심 공연(즐겨찾기) 기능이 실제로 만들어지는지

`notion/OWNERSHIP.md`엔 "이번에 만들지 않는 것"으로 `member_favorite`이 명시돼 있는데, 구글시트 `요구사항 정의서`/`api 설계서`엔 1차 범위(우선순위 하)로 들어가 있습니다. 프론트는 일단 화면에 하트 버튼을 만들어뒀는데(`GET/POST/DELETE /users/me/favorites`), 백엔드가 실제로 이 3개 API를 만들 계획인지 확인해주세요. 안 만들면 프론트 하트 버튼은 데모에서 빼겠습니다.

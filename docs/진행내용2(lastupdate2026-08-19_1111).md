## 설계 포인트

- 회원 탈퇴는 **row 삭제가 아니라 소프트 삭제**(`status=WITHDRAWN`, `withdrawn_at` 기록).
- 탈취된 access 토큰만으로 탈퇴되지 않도록 **비밀번호 재확인**을 요구한다.
- 탈퇴 직후에는 (아직 만료 전인) 기존 access 토큰으로도 더 이상 접근이 안 되도록 `get_current_member`에서 상태를 즉시 확인한다.
- 탈퇴 회원은 비밀번호가 맞아도 로그인 자체를 거부한다.

## `.mypc` 원본 xlsx의 "api 설계서" 시트 발견 + 기존 auth 재설계 (완료)

`docs/sesac_ticket_init.sql` 등과 함께 `.mypc`에 있던 `[새싹] 티켓팅 프로그램.xlsx`를 열어보니
**"api 설계서" 시트**에 AUTH-001~014 전체 스펙이 이미 정의되어 있었음 (`openpyxl`로 직접 읽어 확인).
사용자가 물어본 AUTH-004~007이 정확히 일치했고, 그 김에 기존 로그인/로그아웃/재발급도
설계서와 얼마나 다른지 대조함.

### 발견한 핵심 불일치 (설계서 vs 기존 구현)

| 항목 | 설계서 | 기존 구현 |
|---|---|---|
| 로그인 응답 | `{ accessToken, tokenType, expiresIn }` — refreshToken은 body에 없음 | `{ access_token, refresh_token, token_type }` |
| refreshToken 저장 | **HttpOnly + Secure + SameSite 쿠키** | JSON body로 클라이언트가 직접 보관 |
| 필드 표기 | camelCase | snake_case 계열 |
| `valkey 키 설계서` | `auth:refresh:{memberId}` | 이미 동일하게 구현되어 있었음 (일치 확인) |

→ 사용자가 "이 기회에 기존 auth도 설계서에 맞게 수정"으로 결정.

### 구현 내용

**보안 모델 전환:** refreshToken을 JSON body 대신 **HttpOnly + SameSite=Lax 쿠키**로 발급/검증하도록 로그인/재발급/로그아웃 전면 재작성. 응답 필드는 pydantic `alias_generator=to_camel` + `populate_by_name=True`로 camelCase 직렬화(요청은 camelCase/snake_case 둘 다 허용).

| 파일 | 내용 |
|---|---|
| `core/config.py` | `cookie_secure`, `password_reset_ttl_sec`, `email_verification_ttl_sec`, `email_verification_cooldown_sec` 추가 |
| `core/exceptions.py` | `AUTH_PASSWORD_RESET_TOKEN_INVALID`(400), `AUTH_EMAIL_VERIFICATION_CODE_INVALID`(400), `AUTH_EMAIL_VERIFICATION_TOO_MANY_REQUESTS`(429) 추가 |

### 보안 설계 포인트

- 비밀번호 재설정/이메일 인증 요청은 **가입 여부와 무관하게 항상 200** 응답 (사용자 열거 공격 방지)
- 비밀번호 재설정 토큰/이메일 인증 코드는 **1회용** (사용 즉시 삭제, 재사용 시 실패)
- 비밀번호 재설정 성공 시 **기존 refresh 세션 강제 폐기** (재로그인 유도)
- 이메일 인증 재요청에 **쿨다운**(기본 60초) 적용 — 설계서의 "429 재요청 과다" 대응

### 검증

`pytest tests/` **18개 전부 PASSED** (기존 11개 + 신규 7개). 쿠키 발급/전달 확인을 위해
실제 HTTP 흐름으로도 재검증: 로그인 응답에 `refreshToken` 미노출 + `client.cookies`에
쿠키로 존재 확인, `accessToken/tokenType/expiresIn` 필드명이 설계서와 정확히 일치.

### 남은 불일치 (이번엔 손대지 않음, 필요 시 별도 진행)

- `valkey 키 설계서`의 `queue:{performanceId}:{scheduleId}` vs 구현된 `queue:sorted:{scheduleId}`
  (performanceId 없이 scheduleId만 사용 중 — B의 대기열 연동 시 재검토 필요)
- `admin:refresh:{adminId}` — 관리자 로그인은 현재 refresh 토큰 없이 access 토큰만 발급

## 회원 API 설계서 정합화 2차 — 경로/본인인증/관심공연 (완료)

"왜 설계서대로 안 만들어졌나" 질문에 답한 뒤, "구현 가능하면 설계서대로 모두 고쳐줘"
요청에 따라 회원 관련 나머지 불일치도 해결. 3가지 결정 필요 지점을 먼저 확인받음:

1. **회원탈퇴 비밀번호 확인** → 유지하기로 결정 (설계서엔 없는 보안 강화, 응답 형식만 맞춤)
2. **`preferredGenres`(선호 장르)** → 스키마 변경(B와 공유 중인 `init.sql` 수정) 필요해서
   **이번엔 제외**하고 나머지만 진행
3. **관심 공연(`member_favorite`, AUTH-010~012)** → **지금 구현** (raw SQL 조회로, B의
   performance ORM 모델 없이도 가능)

### 구현 내용

| 파일 | 내용 |
|---|---|
| `domains/member/router.py` | prefix `/member` → **`/users`**로 변경 (설계서 경로 일치). 관심 공연 3개 엔드포인트 추가 |
| `domains/member/service.py` | `update_my_info`에 **`verification_code` 필수 검증** 추가 (AUTH-009 "본인 인증 필요"). `list_favorites`/`add_favorite`/`remove_favorite` 추가 |
| `domains/member/schema.py` | `MemberResponse`/`MemberUpdateRequest`도 camelCase로 전환. `UpdateResponse{updated}`, `WithdrawResponse{deleted}`, `FavoriteItem`, `FavoriteListResponse{content,totalElements}`, `FavoritedResponse{favorited}` 추가 |
| `domains/member/favorite_repository.py` (신규) | `member_favorite`/`performance`/`performance_image`를 **raw SQL(Core text())로만** 조회 — B가 나중에 `domains/performance` ORM 모델을 만들 때 테이블명 충돌 방지 목적으로 의도적으로 ORM 미사용 |
| `core/exceptions.py` | 새 접두사 **`MEMBER_*`** 추가 (`MEMBER_FAVORITE_ALREADY_EXISTS` 409, `MEMBER_FAVORITE_NOT_FOUND` 404) |

| `tests/test_member.py`, `tests/test_email_verification.py` | 경로를 `/users/me`로, 응답 필드를 camelCase로 수정 |
| `tests/test_favorites.py` (신규) | 등록→목록 반영, 존재하지 않는 공연 404, 중복등록 409, 미등록 삭제 404, 삭제 후 목록 반영 — 5개 케이스 |
| `docs/api-contract.md` | 회원 섹션 전체를 새 경로/응답 형식으로 갱신 |

### 설계 포인트

- **PATCH /users/me는 이제 verificationCode 없이는 항상 실패한다.** 클라이언트는 반드시
  먼저 `POST /auth/email/verify-request`로 코드를 받아야 하며, 코드는 1회용으로 소모된다.
- **`performance`/`performance_image`를 ORM으로 등록하지 않은 이유**: B가 나중에
  `domains/performance/model.py`에서 같은 테이블명으로 `Base`를 상속하는 모델을 만들 때,
  같은 `Base.metadata`에 테이블이 두 번 등록되면 `InvalidRequestError`가 난다. raw SQL로만
  다루면 이 충돌을 원천 차단하면서도 지금 당장 기능은 완성할 수 있다.

## 전체 API 설계서(48개) 재감사 + 대기열 전면 재작성 (완료)

사용자가 "처음에 자료 다 줬는데 안 읽었다"고 정당하게 지적함. `.mypc` xlsx의 "api 설계서"
시트 **전체 48개 API**를 처음으로 통째로 뽑아 A 담당 범위(회원/인증, 트래픽 제어, 서버관리자
중 로그인 부분, 시스템 공통) 전체를 재감사함.

### 추가로 발견한 불일치

| API | 문제 |
|---|---|
| TRF-001(대기열 진입) | req에 `performanceId` 누락, 응답이 `queueToken` 기반이어야 하는데 회원 기반으로 구현했었음 |
| TRF-002(순번 조회) | `GET /queue/{queueToken}/status`, **인증 불필요**인데 `GET /queue/status?scheduleId=`로 인증까지 요구하게 만들었었음 — 설계 자체가 다름 |
| ADMIN-007(관리자 로그인) | 경로가 `/admin/auth/login`인데 `/admin/login`으로 만듦 |
| ADMIN-008(관리자 토큰 재발급) | 아예 미구현 |
| SYS-001/002(health) | 응답이 `{status:"UP"}` 이어야 하는데 `{status:"ok"}`/`{status:"ready"}`로 만듦 |
| SYS-003(버전 조회) | 아예 미구현 (분담표는 `app_version` 범위 밖이라 했었음 — 관심공연 때와 같은 상충 케이스) |

### 사용자 결정 3가지

1. **대기열 전면 재작성** → 설계서대로 (권장 선택)
2. **SYS-003 버전 API** → DB 테이블 없이 설정값(.env) 기반으로 간단히 구현
3. **작업 진행 방식**: 지금처럼 다 모아서 한번에 보고하지 말고, **하나씩 끊어서 진행** (사용자가 브랜치 분리 의미가 퇴색된다고 지적) → 이후 관리자/시스템은 각각 끝날 때마다 멈춰서 보고하기로 함

### 대기열 재작성 내용 (완료, 테스트 통과)

**핵심 변경:** member_id 기반 조회 → **queueToken 기반 조회**로 전환. 상태 조회는 이제 인증이 필요 없다.

| 파일 | 내용 |
